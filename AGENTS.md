# Project guidance

## Scope and safety

- Treat this as an npm-workspaces TypeScript monorepo: `server/` is the Express/PostgreSQL API, `web/` is the React SPA, and `bot/` is the Telegram service.
- Start from the named route, component, service, schema, migration, or failing check. Use `README.md` and the nearest `PROJECT_MAP.md`; do not scan the whole repository.
- Preserve user changes. Do not edit unrelated files, commit, or push unless explicitly requested.
- Never edit `node_modules/`, `dist/`, `coverage/`, `playwright-report/`, `test-results/`, generated artifacts, vendored code, or autogenerated `.codex/environments/environment.toml`.
- Do not create task, plan, architecture, status, or process-report files. Keep working notes in the session.
- Use `$feature-development` for feature implementation and substantial fixes.

## Architecture and contracts

- Backend uses Express routes -> services -> repositories -> Knex/PostgreSQL. Keep validation in existing Zod schemas and authorization in existing middleware/policies. Add migrations under `server/src/db/migrations`; never rewrite an applied migration.
- API contracts are defined by server routes, Zod schemas, shared TypeScript types, and web API call sites. For full-stack work, define request, response, errors, auth, and compatibility before implementation.
- Frontend uses React 19, TypeScript, React Router, MUI, shared API/auth/i18n/theme modules, and local MobX stores where established. Reuse existing components/state patterns and add locale keys for new visible text.
- Bot follows its route/service/repository split and Vitest conventions. Treat bot work as backend unless explicitly separated.
- Keep changes small, typed, and consistent with neighboring code. Add no abstraction, dependency, endpoint, or state system without demonstrated need.

## Verification

- Run only checks relevant to changed modules and report commands and results.
- Web: `npm run -w @scheduletm/web typecheck`, `npm run -w @scheduletm/web lint`, targeted `npm run -w @scheduletm/web test:e2e:contracts`; use UI E2E only for affected flows. `npm run -w @scheduletm/web build` is the production check.
- Server: `npm run -w @scheduletm/server typecheck`, targeted `npm run -w @scheduletm/server test -- <test-file>`, then package test/build when risk warrants. `qa:server` runs migrations and needs a configured database; do not run it by default.
- Bot: `npm run -w @scheduletm/bot typecheck`, targeted `npm run -w @scheduletm/bot test -- <test-file>`, then package test/build when warranted.
- Use root lint/typecheck/test/build only for cross-package or high-risk changes.

## Review guidelines

- Review changed and directly connected files only. Prioritize correctness, RBAC, tenant/account scoping, validation, migration safety, API compatibility, i18n, regression coverage, and protected paths.
- One agent owns a file at a time. Limit test/review remediation to two cycles; then report the blocker and request direction.
